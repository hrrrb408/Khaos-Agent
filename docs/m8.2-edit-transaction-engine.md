# M8.2 Edit Transaction Engine

## Scope

M8.2 adds a typed, generation-bound transaction boundary for Coding-mode
multi-file edits. It supports `CREATE`, `UPDATE`, `DELETE`, and `RENAME`.
`COPY` remains outside this milestone because the existing copy authority has
different source/destination and quota semantics.

The implementation is intentionally layered over the existing workspace
authority. It does not add a second file store, journal, recovery directory,
or storage quota implementation:

```text
ToolRegistry / ToolInvocationBroker
  -> AuthorizationResource + published-plan FILE_TRANSACTION role
  -> EditTransactionService
  -> WorkspaceManager.mutate_with_storage_authority()
  -> WorkspaceStorageAuthority
  -> SafeWorkspaceFS / WorkspacePathHandle
```

`TaskWorkspace.generation` is the server-owned write generation used for the
transaction CAS. M8.1 `RepositoryGeneration` and the derived index generation
remain intelligence freshness projections; they are not write authority.

## Contract

`EditTransaction`, `EditOperation`, and `TextEdit` are frozen slot dataclasses.
The transaction digest covers the transaction identity, base generation,
expected workspace digest, operation order, expected file state, content, and
text edits. Authorization resources hash file payloads without disclosing
their content.

Each apply operation is required to carry an explicit expected state:

- `CREATE`: `expected_exists=false` and bounded UTF-8 content.
- `UPDATE`: `expected_exists=true` plus an expected SHA-256 digest, followed by
  either complete replacement content or bounded non-overlapping text edits.
- `DELETE`: `expected_exists=true` plus an expected SHA-256 digest.
- `RENAME`: an existing source with an expected SHA-256 digest and an absent,
  distinct destination.

Paths are normalized NFC POSIX-relative paths. NUL bytes, dot components,
Windows drive/UNC forms, backslashes, protected workspace metadata, duplicate
case-folded targets, and unbounded operation/content/edit counts are rejected.
The transaction API requires parent directories to already exist; directory
creation remains owned by the existing workspace primitives and is not
implicitly added to a file transaction.

## Preview and apply

`preview_edit_transaction` is read-only. It binds to the current generation,
checks an optional workspace digest, prepares every operation, and returns a
bounded deterministic unified diff plus predicted workspace digest. It never
advances generation or publishes a file.

`apply_edit_transaction` runs through the existing per-workspace storage lock
and quota authority. Before the first publish it:

1. Captures all source and destination snapshots through dirfd-anchored
   `SafeWorkspaceFS` recovery snapshots.
2. Validates every operation's existence/digest precondition and revalidates
   every captured path after content preparation.
3. Publishes each operation with no-follow, no-replace/native-atomic
   primitives. Each individual file publish is atomic; the multi-file
   transaction is a logical all-or-rollback contract, not a filesystem-level
   multi-file transaction.
4. Verifies every resulting path and the complete bounded workspace digest.
5. Returns a result bound to the transaction digest and `base_generation + 1`.

Any failure after a publish is tracked using the existing
`SafeWorkspaceFS` filesystem-applied phase. The transaction rolls back applied
operations in reverse order, including restoration of a deleted file into a
missing target using a verified no-replace recovery publish. Recovery identity
or content uncertainty raises the existing `WorkspaceStorageViolation` with
`quarantine_required=true`; it is never reported as a successful or ordinary
partial edit.

Successful Coding file-tool mutations and terminally sealed M4 planned
mutations advance the server-owned `TaskWorkspace.generation`, so an older
transaction cannot become current after another writer succeeds.

## Integration and observability

The two tools are registered with closed capability contracts:

- preview: `filesystem.read`, Coding, `task-workspace`, supporting-read role;
- apply: `filesystem.write`, Coding, `task-workspace`, explicit
  `FILE_TRANSACTION` role.

The plan router matches the complete union of transaction source and
destination paths against the published workspace step. Permission,
approval, sandbox, storage, and dispatch-fence checks remain independent and
are still applied by their existing owners.

AgentLoop injects the service only for the active, scoped `TaskWorkspace` and
invalidates repository intelligence after a successful apply. M8.0 metrics
classify preview as context and apply as a patch attempt. A successful
transaction emits bounded, exact CREATE/UPDATE/DELETE/RENAME mutation events
for incremental intelligence refresh; if an event cannot be projected safely,
the service uses the existing conservative full-refresh path.

## Verification boundary

Regression coverage exercises immutable/digest-bound contracts, deterministic
no-write preview, all four operations, stale generation refusal, complete
precondition validation before publish, mid-transaction rollback, post-publish
failure recovery, storage-authority quota rollback, legacy Coding file-tool
adapter recovery, resource payload binding, and published-plan role matching.
Static compilation, Ruff, focused tests, and the relevant workspace/coding
suites are local evidence; commit, exact-SHA push, and remote CI evidence are
recorded separately in the M8.2 adversarial review report.
